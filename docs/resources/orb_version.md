# circleci_orb_version (Resource)

Publishes a version of a CircleCI orb.

!> **Publishing is permanent and cannot be undone.** A published orb version is immutable: its source cannot be edited, it cannot be republished with different source, and the CircleCI API has **no route to delete or unpublish it**. That is deliberate — anyone who pinned `<namespace>/<orb>@<version>` must keep resolving it forever.

Read the [Lifecycle](#lifecycle) section before using this resource. Its behaviour differs from an ordinary Terraform resource in ways that matter.

## Availability

| | |
| --- | --- |
| **CircleCI Cloud** | Yes |
| **CircleCI Server** | No — served by the CircleCI v3 API, which a Server installation does not route to its public API service. Using this with `deployment = "server"` reports an explicit error at plan time rather than the confusing HTTP 404 the request would otherwise produce. |
| **API** | `POST /api/v3/orb/versions`, `GET /api/v3/orb/versions/{id}`, `GET /api/v3/orb/versions/{id}/source` |
| **Organization type** | Any. |
| **Token** | A personal API token belonging to an organization admin. |

## Example Usage

```terraform
resource "circleci_orb_namespace" "example" {
  name   = "acme"
  org_id = "00000000-0000-0000-0000-000000000000"
}

resource "circleci_orb" "example" {
  namespace_id = circleci_orb_namespace.example.id
  name         = "node"
}

# Publishing is permanent: a published orb version cannot be edited, republished
# with different source, or deleted. `terraform destroy` only forgets it.
resource "circleci_orb_version" "v1_0_0" {
  orb_id  = circleci_orb.example.id
  version = "1.0.0"
  yaml    = file("${path.module}/orb.yml")
}

# To change the source, publish another version. The previous one stays
# published, which is what lets pipelines pin to it.
resource "circleci_orb_version" "v1_0_1" {
  orb_id  = circleci_orb.example.id
  version = "1.0.1"
  yaml    = file("${path.module}/orb.yml")
}

# A dev version is the exception: it is mutable and expires, so editing the YAML
# of a dev version works. Use one while iterating.
resource "circleci_orb_version" "dev" {
  orb_id  = circleci_orb.example.id
  version = "dev:alpha"
  yaml    = file("${path.module}/orb.yml")
}

output "orb_reference" {
  description = "What a .circleci/config.yml should reference."
  value       = "${circleci_orb.example.full_name}@${circleci_orb_version.v1_0_1.version}"
}
```

## Lifecycle

**`terraform destroy` does not delete anything.** There is no API route to delete an orb version, so destroying this resource removes it from Terraform state and emits a warning saying that the version remains published and remains resolvable by every project that references it. Nothing is deleted, and nothing can be.

A direct consequence: **recreating the resource with the same `version` will fail**, because the version already exists. The provider annotates that failure with an explanation rather than passing the raw API error through.

**Changing `version` publishes an additional version.** The previous version stays published — that is the point of an immutable registry. Terraform replaces the resource, the destroy is the no-op above, and the create publishes the new version.

**Changing `yaml` for a stable version is rejected.** Terraform plans a replacement, the destroy does nothing, and the create is refused because that version is already published. To ship new source, bump `version`.

**Dev versions are the exception.** A version named `dev:<label>` is mutable and expires on its own, so a `yaml` change works: Terraform replaces the resource and the API accepts the republish. Use a dev version while iterating, and publish a stable semantic version when the source is settled.

**`yaml` is never refreshed from the API.** CircleCI normalizes the source it stores, so refreshing `yaml` from the server would look like permanent drift. The stored source is exposed separately as the computed `source` attribute. The one exception is immediately after an import, where `yaml` is seeded from `source` so that the resource has complete state.

## Promotion

The v3 API can promote a `dev:<label>` version to a stable semantic version. That is not modelled as a resource, because promotion creates a *new* version rather than changing an existing one, and Terraform has no way to express "promote whatever is there now" idempotently. To publish a stable version from Terraform, declare a `circleci_orb_version` with the semantic `version` you want.

## Schema

### Required

- `orb_id` (String) Unique identifier (UUID) of the orb to publish against, for example `circleci_orb.example.id`. Changing this publishes against a different orb, so it forces a new resource.
- `version` (String) The version to publish: a semantic version such as `1.2.3`, or `dev:<label>` for a mutable dev release. Changing this publishes a new version; the previous version stays published.
- `yaml` (String) The orb source YAML to publish, for example `file("${path.module}/orb.yml")`. This is write-only input: it is never refreshed from the API, because CircleCI normalizes what it stores and the normalized form would otherwise look like permanent drift. Read `source` to see what CircleCI actually stored.

Changing this forces a new resource, which the API accepts only for a `dev:<label>` version. For a stable version, bump `version` as well.

### Read-Only

- `created_at` (String) When the version was published, as an RFC 3339 timestamp.
- `id` (String) Unique identifier (UUID) of the orb version.
- `orb_name` (String) Fully qualified name of the orb this version belongs to, `<namespace>/<orb>`.

No orb version route reports this, so it is resolved with a second request against the orb itself. That lookup is best effort: if it fails the version is still recorded, with this attribute empty, rather than a just-published version being lost.
- `source` (String) The YAML source CircleCI stored for this version, as returned by the API. It may differ from `yaml` by normalization.

## Import

The import ID is the orb version's UUID. Resolve one from an orb id and a version string with the `circleci_orb_version` data source.

```shell
# The import ID is the orb version UUID. Resolve one from an orb id and a version
# string with the circleci_orb_version data source.
terraform import circleci_orb_version.v1_0_0 "44444444-4444-4444-4444-444444444444"
```

After an import, `yaml` holds the source CircleCI stored. If the `yaml` in your configuration differs from it only by normalization, Terraform will plan a replacement that the API rejects; add `lifecycle { ignore_changes = [yaml] }` in that case.
