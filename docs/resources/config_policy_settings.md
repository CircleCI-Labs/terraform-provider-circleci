# circleci_config_policy_settings (Resource)

Controls whether CircleCI evaluates a policy context's config policies. This is the switch that turns enforcement on: uploading policies with `circleci_config_policy_bundle` does not, by itself, enforce anything.

Works against both **CircleCI Cloud and CircleCI Server** — policy decision settings are served by the v2 API. Note the plan and version requirements below.

> **Requires the Scale plan on CircleCI Cloud**, or **CircleCI Server 4.2 or later**.

## Example Usage

```terraform
# Turn on config policy evaluation for the organization. Every pipeline's
# configuration is then checked against the bundle before it runs.
resource "circleci_config_policy_settings" "config" {
  owner_id = "00000000-0000-0000-0000-000000000000"
  enabled  = true

  # Never enable enforcement before the policies exist: with an empty bundle
  # nothing is blocked, but the ordering matters when both are created at once.
  depends_on = [circleci_config_policy_bundle.config]
}

resource "circleci_config_policy_bundle" "config" {
  owner_id = "00000000-0000-0000-0000-000000000000"

  policies = {
    "allow-docker.rego" = file("${path.module}/policies/allow-docker.rego")
  }
}

# The custom policy context has its own switch.
resource "circleci_config_policy_settings" "custom" {
  owner_id       = "00000000-0000-0000-0000-000000000000"
  policy_context = "custom"
  enabled        = false
}
```

## Schema

### Required

- `enabled` (Boolean) Whether config policies are evaluated for this policy context. Enable it only once the bundle holds the policies you intend to enforce: with an empty bundle nothing is blocked, but with an unreviewed one pipelines can start failing immediately.
- `owner_id` (String) Unique identifier (UUID) of the organization whose policy decisions are configured. Changing this value forces a new resource to be created.

### Optional

- `policy_context` (String) Which policy context these settings apply to. Defaults to `config`. Changing this value forces a new resource to be created.

~> A policy context is **not** a CircleCI context: it is a namespace for a bundle of policies, unrelated to `circleci_context`. Its only valid values are `config`. CircleCI documents a `custom` context, but every the API route rejects it with a 400, so it is not offered here.

## What enabling does

While `enabled = true`, every pipeline's configuration is evaluated against the policy context's bundle before the pipeline runs. A configuration that produces a hard failure is blocked; one that produces a soft failure runs but is recorded in the decision log.

Enable it only once the bundle holds the policies you intend to enforce. An empty bundle blocks nothing, so enabling first is safe in that case — but enabling against an unreviewed bundle can start failing pipelines immediately.

## Destroy does not disable

Destroying this resource removes it from Terraform state and **leaves policy evaluation exactly as it is**. The provider makes no API call, and warns to say so.

That is deliberate: turning a security control off as a side effect of removing a Terraform resource is the kind of change nobody wants to discover from a build that stopped being checked. If you want enforcement disabled, set `enabled = false` and apply before removing the resource.

## Only one toggle

CircleCI's decision settings expose a single field, `enabled`. There is no separate "enforcement mode" or "hard fail" switch at this level — whether a violation blocks a pipeline or merely records a warning is decided by the policies themselves, through the `hard_fail` and `soft_fail` rules in your Rego.

## Import

Import is supported using `owner_id`, which assumes the default `config` policy context:

```shell
terraform import circleci_config_policy_settings.config "00000000-0000-0000-0000-000000000000"
```

or `owner_id/policy_context` for any other context:

```shell
terraform import circleci_config_policy_settings.custom "00000000-0000-0000-0000-000000000000/custom"
```
