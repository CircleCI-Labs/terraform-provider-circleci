# circleci_oidc_custom_claims (Resource)

Customizes the claims of the OIDC identity tokens CircleCI issues to jobs, so that a cloud provider or secrets manager will accept them.

## Availability

| | |
| --- | --- |
| **CircleCI Cloud** | Yes |
| **CircleCI Server** | Yes on CircleCI Server 4.4 and later. Not available in air-gapped installations. **Reasoned rather than measured**: no CircleCI Server installation has been available to test against, so this is derived from which routes a Server installation exposes. See the CircleCI Server note on the provider index page. |
| **API** | `GET`, `PATCH` and `DELETE /api/v2/org/{org_id}/oidc-custom-claims`, and the same three on `/api/v2/org/{org_id}/project/{project_id}/oidc-custom-claims` |
| **Organization type** | Any. |
| **Token** | A personal API token belonging to an organization admin. |

## Example Usage

```terraform
# Organization-wide claims: every job in the organization gets these unless a
# project overrides them.
resource "circleci_oidc_custom_claims" "org" {
  org_id   = "00000000-0000-0000-0000-000000000000"
  audience = ["sts.amazonaws.com"]
  ttl      = "1h"
}

# Project-level claims take precedence over the organization's, so a project that
# needs a different audience or a shorter-lived token declares its own.
resource "circleci_oidc_custom_claims" "project" {
  org_id     = "00000000-0000-0000-0000-000000000000"
  project_id = "11111111-1111-1111-1111-111111111111"
  audience   = ["https://vault.example.com"]
  ttl        = "15m"
}

# Only the audience is managed here; the token lifetime stays at CircleCI's
# default.
resource "circleci_oidc_custom_claims" "audience_only" {
  org_id     = "00000000-0000-0000-0000-000000000000"
  project_id = "22222222-2222-2222-2222-222222222222"
  audience   = ["my-identity-provider"]
}
```

## Schema

### Optional

- `audience` (Set of String) The values placed in the token's `aud` claim, replacing CircleCI's default audience. Set it to the audience your identity provider expects, for example `["sts.amazonaws.com"]` for AWS. An empty set is sent as an explicit empty audience; omit the attribute entirely to leave the claim at CircleCI's default. Order is not significant: CircleCI does not preserve the order the audience is sent in.
- `org_id` (String) The unique identifier (UUID) of the organization that owns this OIDC claim customization.

This is the same field as the deprecated `organization_id`; set exactly one of the two.

Changing this value forces a new resource to be created.
- `organization_id` (String, Deprecated) The unique identifier (UUID) of the organization that owns this OIDC claim customization.

~> **Deprecated in favour of `org_id`**, which matches CircleCI's own naming. Both work and mean the same thing; set exactly one. Switching from this attribute to `org_id` does not replace the resource.
- `project_id` (String) Unique identifier (UUID) of the project whose identity tokens are customized. Omit it to customize the organization's tokens instead. Changing this value forces a new resource to be created.
- `ttl` (String) How long an identity token stays valid, as a duration string: one or more unit-suffixed numbers with no separator, for example `1h`, `90m` or `1h30m`. The accepted units are `ns`, `us`, `ms`, `s`, `m` and `h`.

~> **`d` and `w` are not accepted, despite appearing in CircleCI's OpenAPI document.** That document gives this field the pattern `^([0-9]+(ms|s|m|h|d|w)){1,7}$`, but nothing enforces it and the API parses the value with Go's duration parser, which has no unit longer than an hour. `7d` is rejected with `400`; write `168h` instead. This provider rejects it at plan time rather than letting the apply fail.

The API rewrites whatever it is given into its own canonical form, so `90m` is stored and reported as `1h30m0s`. That is not a change: the three spellings compare equal, and no diff is planned for one.

### Read-Only

- `audience_updated_at` (String) The timestamp when the audience claim was last written.
- `ttl_updated_at` (String) The timestamp when the ttl claim was last written.

## One resource, two scopes

CircleCI exposes organization-level and project-level claims on two routes that differ only by an extra `/project/{id}` segment. They take the same request body and answer with the same shape, so this provider models them as a single resource with an optional `project_id` rather than as two resources whose schemas would be identical. Set `project_id` for project claims; omit it for organization claims.

Project-level claims take precedence over organization-level ones, which means an organization-scoped instance and a project-scoped instance can safely coexist.

## A settings object, not an entity

CircleCI always has a claim customization record for every organization and project, so there is nothing to create and nothing that can be "missing". That has three consequences worth knowing:

* **Create is a `PATCH`.** Applying the resource writes the claims you set; it does not create anything.
* **Destroy resets.** Unlike most settings objects, resetting is a real operation here: destroying the resource calls the delete route, and jobs go back to receiving CircleCI's default audience and token lifetime. Only the claims this resource manages are reset, so a claim you never declared is left alone.
* **A reset made elsewhere reads as "gone".** Because an uncustomized scope answers `200` with no claims rather than `404`, the provider treats an empty customization as a removed resource and plans to recreate it.

## The resource is authoritative

The write route is a partial update: a field it does not carry is left alone. Removing `ttl` from your configuration therefore *cannot* mean "stop managing the token lifetime" — there would be no way to ever change it back. It means "reset it", and the next apply deletes that claim.

Declare both claims in one resource, or split them across scopes. Do not point two instances at the same `organization_id` and `project_id`.

## Import

Import is supported using `organization_id` for organization-level claims:

```shell
terraform import circleci_oidc_custom_claims.org "00000000-0000-0000-0000-000000000000"
```

or `organization_id/project_id` for project-level claims:

```shell
terraform import circleci_oidc_custom_claims.project "00000000-0000-0000-0000-000000000000/11111111-1111-1111-1111-111111111111"
```
