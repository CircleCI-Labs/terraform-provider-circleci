# circleci_webhook (Resource)

Manages a CircleCI webhook. Webhooks send HTTP POST payloads to a configured URL when specific events occur in a project.

## Example Usage

```terraform
resource "circleci_webhook" "example" {
  name           = "my-webhook"
  url            = "https://example.com/webhook"
  signing_secret = "my-signing-secret"
  scope_id       = "00000000-0000-0000-0000-000000000000"
  scope_type     = "project"
  events         = ["workflow-completed", "job-completed"]
  verify_tls     = true
}
```

### Keeping the signing secret out of state

`signing_secret_wo` is a write-only alternative to `signing_secret`, available with
Terraform 1.11 or later. Set exactly one of the two.

```terraform
variable "webhook_signing_secret" {
  type      = string
  sensitive = true
}

resource "circleci_webhook" "write_only" {
  name = "my-webhook"
  url  = "https://example.com/webhook"

  signing_secret_wo         = var.webhook_signing_secret
  signing_secret_wo_version = 1

  scope_id   = "00000000-0000-0000-0000-000000000000"
  scope_type = "project"
  events     = ["workflow-completed", "job-completed"]
}
```

The trade between the two is a real one, in both directions:

* `signing_secret` is recorded in Terraform state in cleartext, and rotating it is
  just editing the value — Terraform sees the change and applies it.
* `signing_secret_wo` is sent to CircleCI and then discarded: it appears in neither
  state nor the plan file. But because nothing derived from it is stored, Terraform
  cannot see that it changed, so **`signing_secret_wo_version` must be incremented
  every time the secret changes**. Editing `signing_secret_wo` on its own produces no
  diff and is never sent. Incrementing the version updates the webhook in place; it
  is not recreated.

Neither spelling can be read back. CircleCI masks the signing secret on every
response, so `signing_secret` in state is always the configured value rather than a
live read, and importing a webhook leaves the secret to be supplied afterwards.

## Schema

### Required

- `events` (Set of String) The events that will trigger the webhook. Valid values are: job-completed, workflow-completed. Order is not significant: CircleCI returns the events in an order of its own, so this is a set rather than a list.
- `name` (String) The name of the webhook.
- `scope_id` (String) The ID of the scope (project) for which the webhook is configured. Changing this value forces a new resource to be created.
- `scope_type` (String) The type of the scope. Currently only 'project' is supported. Changing this value forces a new resource to be created.
- `url` (String) The URL to which webhook payloads will be sent. Must be a valid HTTPS URL and cannot point to localhost or private IP addresses.

### Optional

> **NOTE**: [Write-only arguments](https://developer.hashicorp.com/terraform/language/resources/ephemeral#write-only-arguments) are supported in Terraform 1.11 and later.

- `signing_secret` (String, Sensitive) The secret used to sign webhook payloads.

It is recorded in Terraform state in cleartext. Use `signing_secret_wo` instead to keep it out of state, at the cost of having to bump `signing_secret_wo_version` to rotate it. Set exactly one of the two.
- `signing_secret_wo` (String, Sensitive, [Write-only](https://developer.hashicorp.com/terraform/language/resources/ephemeral#write-only-arguments)) The secret used to sign webhook payloads, as a write-only argument: Terraform sends it to CircleCI but never records it in state or in a plan file. Requires Terraform 1.11 or later.

Because nothing derived from the secret is stored, Terraform cannot see that it changed. `signing_secret_wo_version` is required alongside it, and must be incremented every time this value changes, or the new secret is never sent.

Set exactly one of `signing_secret` and `signing_secret_wo`.
- `signing_secret_wo_version` (Number) Rotation counter for `signing_secret_wo`. Increment it whenever `signing_secret_wo` changes: a write-only value leaves no trace in state, so this is the only thing Terraform has to compare, and changing `signing_secret_wo` on its own is not a change as far as Terraform is concerned.

Required when `signing_secret_wo` is set, and must be at least 1. Incrementing it rewrites the signing secret in place.
- `verify_tls` (Boolean) Whether to verify TLS certificates when sending payloads. Defaults to true.

### Read-Only

- `created_at` (String) The timestamp when the webhook was created.
- `id` (String) The unique identifier of the webhook.
- `updated_at` (String) The timestamp when the webhook was last updated.

## Import

Import is supported using `scope_id/webhook_id`:

```shell
terraform import circleci_webhook.example "<scope_id>/<webhook_id>"
```

After import, `scope_type` is automatically set to `"project"` (the only currently supported value), and every other attribute is filled in from a read — except the signing secret. CircleCI never returns it, on any route, so neither `signing_secret` nor `signing_secret_wo` is populated; set one of them in your configuration before running `terraform plan`, or the resource's own validation (exactly one of the two) fails. Because `UpdateWebhook` is a full-replace `PUT` that always sends whatever the configuration currently says, the first apply after import writes that value back over whatever secret is actually configured on CircleCI — there is no read to catch a mismatch first, so prefer sourcing the value from wherever it already lives (a secret manager, through `signing_secret_wo`) over retyping it by hand.
