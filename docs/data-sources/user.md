# circleci_user (Data Source)

Fetches a CircleCI user.

With no `id`, this reports the user the configured API token authenticates as — the usual case: confirming which account a pipeline's token belongs to, guarding against running an apply with the wrong credentials, or recording the identity that created a set of resources. With an `id`, it looks that user up instead.

## Availability

| | |
| --- | --- |
| **CircleCI Cloud** | Yes |
| **CircleCI Server** | Yes. Both routes are served by the long-standing v2 API, which a Server installation's gateway forwards `/api` to by default. **Reasoned rather than measured**: no CircleCI Server installation has been available to test against, so this is derived from which routes a Server installation exposes. See the CircleCI Server note on the provider index page. |
| **API** | `GET /api/v2/me` with no `id`, `GET /api/v2/user/{id}` with one |
| **Organization type** | Not applicable; a user is not scoped to an organization. |
| **Token** | A **personal** API token. See below. |

## A personal token is required

~> **A project or organization token cannot read either route.** Both authorize the *caller* rather than the subject, so the request fails with a permissions error regardless of which user is being requested. `GET /api/v2/me` answers HTTP 403 rather than 401 in that case, which is why the provider reports it as a permissions failure and not as a missing user.

## Why there is no matching resource

CircleCI has no API for creating, updating or deleting a user account, and organization membership is managed in the web UI. There is nothing writable to converge on.

Group membership cannot be managed through this provider either: the routes
exist but are not exposed by the public API. See `circleci_group`'s documentation
for what is and is not possible for a group.

## Example Usage

```terraform
# With no id, this reports the user the configured token authenticates as. The
# usual reason to want it: confirming which account a CI token belongs to before
# letting a pipeline make changes with it.
data "circleci_user" "me" {}

output "authenticated_as" {
  value = data.circleci_user.me.login
}

variable "expected_login" {
  type        = string
  description = <<-EOT
    The VCS login the configured CIRCLE_TOKEN is expected to belong to, for example
    the CI service account. The check below fails the run if it belongs to someone
    else. Not a secret: it is the account's public username.
  EOT
}

# Guard against running with a token nobody expected.
check "expected_service_account" {
  assert {
    condition     = data.circleci_user.me.login == var.expected_login
    error_message = "The configured CIRCLE_TOKEN belongs to ${data.circleci_user.me.login}, not ${var.expected_login}."
  }
}

variable "actor_id" {
  type        = string
  description = <<-EOT
    UUID of the CircleCI user to look up. A pipeline reports the actor that started
    it under `trigger.actor`, and the circleci_pipeline_run data source surfaces it.
  EOT
}

# With an id, it looks that user up instead — for example the actor recorded on a
# pipeline.
data "circleci_user" "pipeline_actor" {
  id = var.actor_id
}

output "pipeline_actor_name" {
  value = data.circleci_user.pipeline_actor.name
}
```

## Schema

### Optional

- `id` (String) Unique identifier (UUID) of the user to fetch. Omit it to fetch the user the configured token authenticates as, in which case this reports that user's ID.

This is a CircleCI user ID, not a VCS user ID. It is the value that appears as the actor on a pipeline or workflow.

### Read-Only

- `avatar_url` (String) URL of the user's avatar on their VCS.
- `login` (String) The user's login on their VCS.
- `name` (String) The user's display name.
