# circleci_pipeline_workflows (Data Source)

Fetches every workflow in a CircleCI pipeline run. Pagination is followed internally, so the result
covers every workflow rather than one page.

This data source completes the chain from a pipeline run down to individual jobs. Both
[`circleci_workflow`](workflow) and [`circleci_workflow_jobs`](workflow_jobs) require a workflow ID,
and until this was added nothing in the provider could produce one — the only way in was to already
know it.

```
circleci_pipeline_run  ->  circleci_pipeline_workflows  ->  circleci_workflow_jobs
```

~> **This is a point-in-time read of mutable runtime state.** `status` changes as each workflow runs,
and the set of workflows can grow while the pipeline is still in flight (a dynamic-config pipeline adds
workflows after its `setup` workflow completes). Use this data source for inspection and in `check`
blocks; using it to derive a resource attribute will cause a perpetual diff.

## Availability

| | |
| --- | --- |
| **CircleCI Cloud** | Yes |
| **CircleCI Server** | Yes — implemented directly in the same v2 API application on both deployments (`the CircleCI API`); see [`circleci_pipeline_run`](pipeline_run). |
| **API** | `GET /api/v2/pipeline/{pipeline-id}/workflow` |
| **Organization type** | Any. |
| **Token** | Any valid API token with permission to view the project's builds. |

-> **`pipeline_id` is a pipeline *run*, not a pipeline definition.** Pass the `id` from
[`circleci_pipeline_run`](pipeline_run), not from the [`circleci_pipeline`](../resources/pipeline)
resource — those are different objects with different identifiers.

## Example Usage

```terraform
# Lists every workflow in a pipeline run. Available on both CircleCI Cloud and
# CircleCI Server.
data "circleci_pipeline_workflows" "this" {
  pipeline_id = "1e2d3c4b-5a69-7887-9a0b-1c2d3e4f5061"
}

# This data source is the link that makes the run -> workflow -> job chain
# usable: circleci_workflow_jobs needs a workflow ID, and nothing else in the
# provider could produce one.
data "circleci_workflow_jobs" "each" {
  for_each = {
    for workflow in data.circleci_pipeline_workflows.this.workflows :
    workflow.name => workflow.id
  }

  workflow_id = each.value
}

output "circleci_failed_workflows" {
  value = [
    for workflow in data.circleci_pipeline_workflows.this.workflows : workflow.name
    if workflow.status == "failed"
  ]
}
```

## Schema

### Required

- `pipeline_id` (String) Unique identifier (UUID) of the pipeline run, as returned by [`circleci_pipeline_run`](pipeline_run). Note this is the ID of a pipeline *run*, not of a [`circleci_pipeline`](../resources/pipeline) definition.

### Read-Only

- `workflows` (Attributes List) The workflows in the pipeline run, in the order the API returns them. (see [below for nested schema](#nestedatt--workflows))

<a id="nestedatt--workflows"></a>
### Nested Schema for `workflows`

Read-Only:

- `canceled_by` (String) Unique identifier (UUID) of the user who canceled the workflow. Null unless it was canceled.
- `created_at` (String) When the workflow was created, as an RFC 3339 timestamp.
- `errored_by` (String) Unique identifier (UUID) of the user whose action errored the workflow. Null unless it errored.
- `id` (String) Unique identifier (UUID) of the workflow. Pass this to [`circleci_workflow_jobs`](workflow_jobs) to read its job graph.
- `name` (String) Name of the workflow, as declared in configuration.
- `pipeline_number` (Number) Number of the pipeline this workflow belongs to.
- `project_slug` (String) Slug of the project this workflow belongs to.
- `started_by` (String) Unique identifier (UUID) of the user who started the workflow.
- `status` (String) Current status of the workflow.
- `stopped_at` (String) When the workflow stopped, as an RFC 3339 timestamp. Null while it is still running.
- `tag` (String) Tag of the workflow, for example `setup` for a setup workflow in a dynamic-config pipeline. Null for an ordinary workflow.
